**Open issue: [#1 — missing `_libwasmtime.so`](https://github.com/felixdorn/mcp-nix/issues/1)**

Confirmed. The Nix build selects `wasmtime-40.0.0-py3-none-any.whl`. Inspecting that exact wheel shows its only native library is `wasmtime/win32-x86_64/_wasmtime.dll`. On Linux, `wasmtime/_ffi.py` instead loads `linux-x86_64/_libwasmtime.so`, which is absent. This is a wrong-wheel selection problem, rather than evidence that an existing Linux library needs a search-path adjustment.

The resulting executable is `/nix/store/saj326k1wy41r28ajy36i6dnbiw4iqqg-mcp-nix/bin/mcp-nix`, matching the path in the issue. Running it reproduces the reported traceback.

Fix the wheel selection in [flake.nix](../flake.nix#L48), with explicit platform-appropriate artifacts if necessary. The Linux and macOS wheels and hashes already exist in `uv.lock`. Add a Nix check that imports registered tools and instantiates the runtime, or performs a stdio smoke test. Building the derivation, running `--help`, or evaluating a flake alone does not exercise this failure. Longer term, replacing Noogle's custom WASM integration may allow removing Wasmtime entirely.

**Reliability and maintainability findings**

1. **Blocking work in async handlers.** Every tool in [tools.py](../mcp_nix/tools.py#L50) is `async def`, but the implementations call synchronous HTTP, indexing, and disk-cache code without yielding. A protocol-level probe with a mocked 250 ms backend delayed an independent 20 ms heartbeat to 251 ms on master and 254 ms on the PR. This impairs parallel calls and timely cancellation. Move networking to an async client or dispatch synchronous work explicitly. A plain change to `def` is insufficient on the locked FastMCP version: its local `FunctionTool.run()` invokes synchronous functions inline. Account for shared caches and the singleton WASM store before adding concurrent workers.

2. **Stale or inconsistent caches.** [NüschtOS chunks](../mcp_nix/nuschtos.py#L185) are cached forever under deployment-relative URLs. Indexes and chunks can then come from different deployments. In-memory indexes in both NüschtOS and Home Manager never expire, bypassing disk TTL refresh for long-lived servers. Use versioned snapshots or coordinated refresh of index and chunks, with bounded memory-cache lifetimes. This deployment-mismatch risk follows from the code; the audit did not stage two upstream deployments to demonstrate it.

3. **Cache keys ignore request parameters.** [Cache.request](../mcp_nix/cache.py#L119) uses only the URL as its key despite accepting `params`, headers, and other request kwargs. A controlled probe requesting `q=a` and then `q=b` returned `a` both times with only one network call. Current adapters mostly embed queries in their URL strings, so treat this as a shared-helper bug and a risk for new integrations rather than an explanation for all current failures.

4. **Incomplete HTTP failure normalization.** [Cache.request](../mcp_nix/cache.py#L103) catches timeout and HTTP status errors but lets connection failures escape as `requests.ConnectionError`; this was reproduced without a network dependency. Convert request failures into the backend error hierarchy and provide useful recovery text. Validate a fresh response before committing it to cache: currently `get_or_set()` writes it before its callback validates it.

5. **Unbounded output and misleading completeness.** `show_option_details` promises all children, while the NüschtOS backend caps its search at 500. Package sources and option subtrees are otherwise returned wholesale. Add pagination or explicit result limits, `total`/`has_more`, and source line ranges. Reserve “all” for a verified exhaustive result.

6. **Documentation drift.** `search_nixpkgs` tells the model to call removed tool `show_nixpkgs_package`. Option-tool descriptions list only seven of the eleven supported projects. `CONTRIBUTING.md` still describes removed `TOOL_CATEGORIES` and default-exclusion machinery. Refresh these descriptions alongside the tool contract, since they directly influence model behavior and contributor changes.

**Current MCP guidance applied to this project**

- **Correct errors first.** Operational and argument failures need actionable content and `isError=true`; “no search matches” can remain successful empty data. This follows the current [MCP tool error guidance](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling). Extend PR #3 with deterministic coverage of all failure branches.
- **Declare read-only behavior.** All nine advertised tools currently have `annotations=null`. Add accurate `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint` values. These tools query external sources, so `openWorldHint=true` is appropriate; they do not modify upstream resources. Annotations remain advisory. See [FastMCP tool annotations](https://gofastmcp.com/docs/servers/tools).
- **Return useful typed data.** FastMCP already supplies an output schema and structured content here, but only as a wrapped prose string, `{"result": "..."}`. Return typed package/option/function records with canonical versions, source URLs, counts, and pagination metadata, while preserving useful text for existing clients. The [MCP structured-content rules](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#structured-content) specify schema consistency.
- **Plan an explicit SDK migration.** The locked SDK advertises versions through `2025-11-25`. The current official revision is `2026-07-28`, which changes discovery, request metadata, and lifecycle behavior. Treat this as a compatibility project, with legacy-client and modern-client transport tests, rather than manually modifying protocol internals. See the [official release notes](https://blog.modelcontextprotocol.io/posts/2026-07-28/) and [FastMCP upgrade guidance](https://gofastmcp.com/docs/getting-started/upgrading/from-fastmcp-2). Supporting an older revision is not itself proof of a defect in its legacy contract.
- **Publish tested dependency bounds.** `fastmcp>=0.1.0` does not express the APIs actually used or protect published installations from incompatible major releases. The repository lock protects contributors, while `uvx mcp-nix` resolves published requirements independently. Test both the chosen lower bound and a supported current version, and align Python support with the Rust extension. Declare directly imported `platformdirs` explicitly instead of relying on FastMCP to pull it in.
- **Keep stdio simple and tested.** Preserve JSON-RPC-only stdout and stderr logging, as required by the [stdio specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio). Add process-level smoke tests and cancellation checks. The [official Inspector CLI](https://modelcontextprotocol.io/docs/tools/inspector) is also suitable for compatibility checks. This local stdio server has no demonstrated need for a hosted HTTP/OAuth redesign.

2. Repair NixOS and Home Manager, then NüschtOS/NixVim, Noogle, nix-nomad, and NixHub. For Noogle and NüschtOS, evaluate replacing custom native bindings with cached published JSON data. This could reduce installation complexity and sensitivity to generated frontend formats.

Assert successful `isError=false` before checking content, and test failure signaling separately. Avoid snapshots of floating source revisions and release catalogs.

The last visible successful Tests run was [8 January 2026](https://github.com/felixdorn/mcp-nix/actions/runs/20833488067); current live failures were not visible in that historical result.
5. Introduce async I/O, coordinated cache refresh, typed results, bounded output, current SDK compatibility, and updated documentation in separately reviewable changes.
